Подготовь и выпусти релиз: **$ARGUMENTS**.

1. Определи версию: если не задана — по semver из коммитов с последнего тега (`git log <tag>..HEAD`): есть `BREAKING CHANGE`/`!` → major; есть `feat` → minor; только `fix`/`refactor`/`perf`/`docs` → patch. Покажи вычисление (какие коммиты дали бамп).
2. Синхронизируй версию во ВСЕХ манифестах проекта (`package.json`, `.claude-plugin/plugin.json` и др. — найди через Grep по текущей версии). Тег обязан равняться версиям манифестов — иначе релиз невоспроизводим.
3. Обнови `CHANGELOG.md` за диапазон (по правилам `/gitflow:changelog`): секцию `[Unreleased]` переведи в `## [X.Y.Z] - <дата>`.
4. Закоммить релизные файлы **поимённо** (`chore(release): vX.Y.Z`) и поставь тег `git tag vX.Y.Z`. Покажи `git status` и `git log --oneline -3`.
5. **СТОП — точка подтверждения.** Покажи план публикации (тег, ветка, release notes) и жди явного «да» владельца. Односложное «ок»/«go» на другой вопрос — не авторизация; переспроси, назвав действие: «пушу коммит+тег и публикую GitHub release vX.Y.Z — подтверди».
6. Только после подтверждения: `git push && git push origin vX.Y.Z`, затем release через GitHub MCP или `gh release create vX.Y.Z --notes-file <notes>`. Отдай URL релиза как доказательство. Нет `gh`/MCP — отдай готовые notes для ручной публикации, пометив это.

Края: нет новых коммитов с последнего тега — релизить нечего, скажи прямо; рабочее дерево грязное чужими правками — стоп и спроси до шага 4.

Опирайся на навык `git-workflow`. Делегируй субагенту `gitflow`.

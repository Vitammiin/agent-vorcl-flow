Наладь мониторинг сервиса: **$ARGUMENTS**.

1. Оцени текущее состояние: чем логирует проект (`console.log` vs pino/winston), есть ли health-эндпоинт, куда уходят логи (stdout / файл), что в `HEALTHCHECK` Docker и health-check хостинга.
2. Структурные логи: pino (или winston с JSON-форматом) → JSON в stdout — контейнерная норма, никаких файлов внутри контейнера. Уровни осознанно (`error`/`warn`/`info`/`debug`), контекст в полях (`requestId`, `userId`, длительность), секреты/PII — под запретом в логах (redact-листы pino).
3. Health-эндпоинт: `GET /health` — liveness (процесс жив, отвечает 200 без внешних зависимостей) и при нуждах `/ready` — readiness (проверка коннекта к БД/Redis с таймаутом). Подключи его в `HEALTHCHECK` Dockerfile/compose и в health-check хостинга.
4. Что алертить (минимальный набор): доля 5xx, p95 латентность, рестарты/OOM контейнера, ошибки коннекта к БД (`ECONNREFUSED`/timeout), заполнение диска/памяти. Для каждого — где смотреть сигнал.
5. На Render метрики (`get_metrics`), логи (`list_logs`) и алерты по сервису — зона агента `render`: сформулируй, что смотреть/алертить, и делегируй ему проверку живого сервиса.
6. Докажи: подними сервис (локально/compose), покажи `curl -s localhost:PORT/health` с ответом и пример JSON-строки лога из stdout.

Края: пустой `$ARGUMENTS` — текущий каталог. Сервис не поднимается локально — сначала первопричина (логи), не наводи мониторинг поверх сломанного. Внешние APM/SaaS — только по явному запросу владельца.

Отдай: изменённые файлы (пути), вывод `curl /health` + пример структурного лога, список алертов, что делегировано `render`. Опирайся на навыки `docker`, `nodejs`, `render`, `backend-architecture`. Делегируй субагенту `devops`.

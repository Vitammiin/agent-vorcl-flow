argument-hint: "[версия или диапазон тегов; по умолчанию последний тег..HEAD]"
allowed-tools: Read, Write, Edit, Bash, Grep, Glob

Собери release notes: **$ARGUMENTS**.

1. Определи диапазон: `git tag --sort=-v:refname` → последний тег..HEAD, либо заданные версия/диапазон. Если тегов нет — спроси, от какой точки считать релиз.
2. Собери **факты**: `CHANGELOG.md` (если ведётся — он первичен) + `git log --oneline <диапазон>` + существенно затронутые области (`git diff --stat`). Ни одного пункта, которого нет в истории или CHANGELOG, — release notes не место для планов.
3. Сгруппируй по Keep a Changelog (навык `technical-writing`): Added / Changed / Fixed / Deprecated / Removed / Security. **Breaking changes — отдельным блоком первыми**, с инструкцией миграции.
4. Пиши для пользователя релиза, не для автора коммита: «что изменилось и что мне делать», а не «refactor utils». Мелкие технические коммиты агрегируй в один пункт.
5. Сверь номер версии с `package.json`/манифестом плагина; расходится — остановись и спроси, не угадывай.
6. Выдай markdown-текст для GitHub release; если проект ведёт `CHANGELOG.md` — добавь туда секцию версии в том же формате. **Сам релиз, теги и push не создавай** — это зона агента `gitflow`; твой продукт — текст.

Края: пустой **$ARGUMENTS** — последний тег..HEAD; пустой диапазон (нет коммитов) — так и скажи, не выдумывай содержание.

Отдай текст заметок + диапазон/число коммитов, из которых он собран (доказательство: фрагмент `git log`). Опирайся на навык `technical-writing`. Делегируй субагенту `docs`.

Создай или обнови `ARCHITECTURE.md`: **$ARGUMENTS**.

1. Прочитай реальную структуру: каталоги, workspaces/пакеты, точки входа, роуты, модели/миграции, конфиги интеграций. Архитектуру описывай **по коду**, не по догадкам — каждый упомянутый модуль/файл проверь на существование (Glob/ls).
2. Разделы: обзор одним абзацем (что за система, из чего состоит) → модули и границы (таблица: модуль → ответственность → ключевые файлы) → data flow (путь запроса через слои до БД и обратно) → схема данных → внешние интеграции → ключевые решения в ADR-формате (context / decision / consequences — кратко, из навыка `technical-writing`).
3. **Диаграммы не рисуй сам вслепую** — делегируй агенту `mermaid` (flowchart для потоков, erDiagram для БД, sequence для взаимодействий; он валидирует реальным рендером). Изощрённые визуальные схемы (swimlane, сложная раскладка) — агенту `drawio`. Ты формулируешь, ЧТО изобразить (узлы, связи, границы), и вставляешь результат mermaid-блоком или ссылкой на файл.
4. Что изображать и на каком уровне детализации — по навыку `system-design`: границы сервисов, синхронные/асинхронные связи, хранилища; не вываливай все файлы на одну схему.
5. Счётчики (число модулей/сервисов/пакетов) — пересчётом реальных каталогов, не по памяти.

Края: пустой **$ARGUMENTS** — весь репозиторий; существующий `ARCHITECTURE.md` — обнови дрейф, сохранив структуру.

Отдай путь к файлу + список полученных от `mermaid`/`drawio` диаграмм (с их рендер-статусом) + сверку упомянутых модулей с реальностью. Опирайся на навыки `system-design`, `technical-writing`. Делегируй субагенту `docs`.

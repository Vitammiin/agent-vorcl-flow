Проведи аудит зависимостей (**read-only**): **$ARGUMENTS**.

1. Найди все `package.json` + lock-файлы (`package-lock.json`/`pnpm-lock.yaml`/`yarn.lock`) — в монорепо аудит по каждому воркспейсу.
2. Прогони `npm audit --json` (или `pnpm audit`/`yarn npm audit` по менеджеру lock-файла). Если реестр недоступен/офлайн — честно скажи, что CVE-проверка не выполнена, и ограничься разбором lock-файла (устаревшие мажоры, заброшенные пакеты); «уязвимостей нет» без прогона не заявляй.
3. Для каждой CVE: пакет, версия, severity из advisory, прямой или транзитивный путь (`npm ls <pkg>`), достижим ли уязвимый код в проекте (dev-only и недостижимые пути — пометь как вероятный false positive, не смешивай с реальными).
4. Оцени фикс: есть ли патч-версия; `npm audit fix` хватит или нужен major bump (ломающее обновление — отдельная задача с изучением changelog); для транзитивных без фикса — `overrides` в `package.json` как временная мера.
5. Каждая находка: пакет@версия, CVE/advisory-ID, severity, путь зависимости, рекомендованное обновление + ломающее ли оно.

Пустой **$ARGUMENTS** — корень репозитория и все воркспейсы. Ничего не устанавливай и не обновляй — только анализ; значимое — в `add_task` на `backend`/`frontend`. В финале — вывод `npm audit` (сводка) как доказательство.

Опирайся на навыки `security-audit`, `workflow`, `task-master`. Делегируй субагенту `security`.
